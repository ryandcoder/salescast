# SalesCast

A sales analytics and forecasting dashboard. It takes historical sales through **cleaning, exploratory analysis, seasonality and trend analysis, a tested forecast, and business recommendations**, and shows each step in one page.

> **About the data:** the bundled dataset (`data/sales.csv`) is **synthetic**. It was generated by `scripts/generate_sales_data.py` with a fixed random seed so the project runs out of the box. It is not real company data, and every number in this README describes that generated dataset. The pipeline works on any CSV with the same columns.

**Stack:** React, TypeScript, Vite, Tailwind CSS, Recharts · Python, FastAPI, Pandas, NumPy, statsmodels · PostgreSQL · Docker Compose

---

## Project overview

SalesCast answers the questions a sales or operations manager would ask:

| Question | Where it is answered |
|---|---|
| How much revenue has been generated, and how is it changing? | Key figures, Sales overview |
| Which categories, products and regions perform best? | Sales by category and region, Products |
| Are there seasonal patterns, and is performance rising or falling? | Seasonality and trend |
| What are expected sales for the next 3, 6 or 12 months? | Sales forecast |
| How accurate is the model, and does it beat a simple baseline? | Forecast accuracy |
| What should management prepare for? | Insights, recommendations, inventory planning |

Everything is calculated from the data when you load the page. Filters (date range, category, product, region) update the historical analysis, and the forecast is always labeled **Overall** or **Filtered** so a filtered forecast is never mistaken for the whole business.

## Business problem

Stock bought too early ties up cash, and stock bought too late means lost sales. A forecast turns past sales into a planning range for the next few months. A forecast is only useful if you know how far to trust it, so SalesCast does not just draw a line. It tests the model on months it never saw, compares it with simple baselines, shows a prediction interval, and says plainly when the data does not support a conclusion.

## Dataset

`data/sales.csv`: 19,243 orders from January 2022 to December 2025, with 24 products, 3 categories (Technology, Furniture, Office Supplies) and 4 regions (West, East, Central, South).

| Column | Meaning |
|---|---|
| `order_id`, `order_date` | Order identifier and date |
| `product`, `category`, `region` | What was sold and where |
| `quantity`, `unit_price`, `discount` | Order details (discount is a fraction, 0 to 1) |
| `sales` | `quantity × unit_price × (1 − discount)` |
| `profit` | Sales minus a fixed cost model per category |

The generator builds in a moderate upward trend (about 8% a year), a yearly seasonal shape with a November and December peak and a January and February dip, and random noise. It also adds **15 duplicate orders and 10 missing discount values on purpose**, so the cleaning step has something real to find. Because the profit costs come from a simple model, profit figures show how the analysis works and say nothing about real margins.

To use your own data, replace `data/sales.csv` with a file that has the required columns (`profit` is optional; if it is missing, the profit section is left out). Run `docker compose down -v` first so the database reloads.

## Data cleaning

`backend/app/analytics/cleaning.py` cleans the file with Pandas when the database is first loaded, and counts every step.

1. Trim text, parse dates, and convert numbers (anything unparseable becomes missing).
2. Remove rows with invalid dates, missing order IDs, missing product/category/region, **duplicate orders** (first kept), non-positive quantities or prices, negative sales, or discounts outside 0 to 1.
3. **Recover missing discounts** from the order's own numbers: `discount = 1 − sales / (quantity × unit_price)`.
4. Check that `sales` agrees with `quantity × unit_price × (1 − discount)` and report any mismatches (reported, never silently changed).

Result on the bundled dataset:

```text
Records:                 19,243
Missing values:          10   (all in discount, all recovered)
Duplicate orders:        15   (removed)
Invalid dates:           0
Records after cleaning:  19,228
Sales formula mismatches: 0
```

The same summary is saved to `data/data_quality_report.json`, served at `/api/data-quality`, and shown at the bottom of the dashboard.

## Exploratory analysis

Everything on the historical side is computed in SQL (PostgreSQL) and Pandas, never hardcoded:

- **Key figures:** total revenue, orders, units, average order value, average monthly revenue, best-selling product, best region, and profit with margin.
- **Revenue, units and orders over time** by month, quarter or year. Monthly revenue also shows a 3-month moving average and a fitted trend line.
- **Category, region and product breakdowns,** each sortable or ranked. The product view deliberately compares *top by revenue* with *top by units*, because the best-selling product by volume is not always the one that earns the most.
- **Seasonality:** average revenue by calendar month, each year overlaid month by month, quarter shares, and yearly growth.
- **Partial months** (for example, when a date filter cuts a month in half) are flagged and left out of the trend and seasonality, so they never look like a sales drop.

**Seasonality is only claimed when the data supports it.** It requires at least 24 complete months, calendar month must explain at least 50% of the variation around the trend (measured on revenue per day, so short months do not create a false pattern), and the best and worst months must differ by at least 15%. Otherwise the dashboard says no pattern is claimed and explains why. A test confirms that random noise is not reported as seasonal.

## Forecasting method

`backend/app/forecasting/model.py`

1. **Monthly series:** daily sales are aggregated to complete months. Partial months at either end are excluded.
2. **Model:** Holt-Winters style exponential smoothing from `statsmodels` (`ETSModel`) with a damped additive trend. A 12-month seasonal component is added **only if** the seasonality check passed and the training window holds at least two full years. It tries a multiplicative seasonal form first, then additive, then no seasonality, and reports which one was used and why.
3. **Train/test split:** the history is split in time order, 80% for training and the most recent 20% (at least 3 months) for testing. The model is fitted on the training months and scored on the test months it has never seen.
4. **Refit and forecast:** after scoring, the model is refit on all complete months and forecasts the next **3, 6 or 12 months** (default 6). No other horizon is accepted.
5. **Prediction intervals:** each forecast month has an 80% interval from the model. The chart shows actual history as a solid line and the forecast as a dashed line inside a shaded future zone with the interval as a band.
6. **Guard rails:** with fewer than 18 complete months the app refuses to forecast and says why. Forecast values are clipped at zero.

Forecasts are cached on the server per filter-and-horizon combination, so the forecast, accuracy and insights endpoints share one model fit.

## Model evaluation

On the held-out test months, Holt-Winters is compared with two baselines:

| Model | What it does |
|---|---|
| Naive | Repeats the last observed month |
| Seasonal naive | Uses the same month one year earlier |

The seasonal baseline matters: on data with a yearly cycle, the plain naive baseline is easy to beat, so the model also has to beat a simple "same month last year" rule to be worth using.

| Metric | Meaning |
|---|---|
| **MAE** | Average size of the monthly miss, in revenue units |
| **RMSE** | Like MAE, but large misses count more |
| **MAPE** | Average miss as a percentage of actual revenue |
| **Interval coverage** | Share of test months inside the 80% interval |

The dashboard prints a plain-language verdict, including *"did not beat the naive baseline"* when that happens.

**Results from a run on the bundled dataset** (fill in from the Forecast accuracy section after your first `docker compose up`):

| Model | MAE | RMSE | MAPE |
|---|---|---|---|
| Holt-Winters | _from the dashboard_ | _from the dashboard_ | _from the dashboard_ |
| Naive | _from the dashboard_ | _from the dashboard_ | _from the dashboard_ |
| Seasonal naive | _from the dashboard_ | _from the dashboard_ | _from the dashboard_ |

**Limitations:** the test window is short (about 10 months on the bundled data), so error figures are noisy. Past accuracy does not guarantee future accuracy. The model uses sales history only, so promotions, price changes and outside events are not modeled. Forecasts are at the level of total revenue for the current selection; there are no product-level forecasts.

## Business findings

These describe the **synthetic** dataset and show the kind of conclusions the dashboard produces. Each is recomputed from whatever data is loaded.

- **Revenue:** $6.63M across 19,228 orders, an average order of $344.59 and about $138k a month.
- **Category mix:** Furniture earns 51% of revenue, Technology 33% and Office Supplies 16%. Office Supplies has the most units but the lowest revenue share, which shows why volume and revenue need separate rankings.
- **Products:** Laptop earns the most revenue; Whiteboard sells the most units.
- **Regions:** West is the strongest region; South contributes 18.5% of revenue, more than 20% below the average region.
- **Seasonality:** a clear yearly pattern. Calendar month explains about 74% of the variation around the trend. November and December run roughly 26 to 28% above a typical month; January and February run about 16 to 23% below.
- **Trend:** the long-run trend is upward, about 9% a year. However, the most recent full year is flat versus the year before, because average order value dipped even as order counts kept growing.
- **Furniture** revenue fell about 3% over the last 12 months compared with the 12 before.
- **Profit:** a 27.8% overall margin; Office Supplies has the highest margin (36.3%) despite the lowest revenue.

## Recommendations

The dashboard generates recommendations from the analysis and shows the evidence for each. Typical ones:

- **Build stock ahead of months the forecast and history both show as strong** (here, November and December).
- **Expect softer demand in historically weak months** (here, January and February) and avoid over-ordering for them.
- **Monitor categories with declining revenue** (here, Furniture).
- **Review underperforming regions** (here, South).
- **Use the forecast as a planning range, not a target,** and lean on last year's same-month sales whenever a simple baseline matched the model.

The inventory section only flags months expected to be at least 10% above or below the recent monthly average. It is informational and is not an inventory optimization system.

## Installation

Requires Docker with Docker Compose.

```bash
docker compose up --build
```

Then open:

- Dashboard: <http://localhost:5173>
- API docs: <http://localhost:8000/docs>
- Health check: <http://localhost:8000/api/health>

On first start the backend creates the `sales` table, cleans the CSV and loads it. The first forecast request fits several models, so the forecast section can take a few seconds to appear. To reload the data from scratch, run `docker compose down -v` and start again.

Database settings come from environment variables; copy `.env.example` to `.env` to change them. Never commit a real `.env`.

### Running the tests

Backend (analytics, cleaning and forecasting logic checked against plain Pandas; runs without PostgreSQL):

```bash
cd backend
pip install -r requirements.txt pytest
python tests/test_analytics.py
python tests/test_forecasting.py
```

The forecasting test that fits the real statsmodels model is skipped automatically if statsmodels is not installed.

Frontend (formatting and chart-data logic; needs Node 22 or newer):

```bash
cd frontend
npm install
npm test
npm run typecheck
```

### API

All data endpoints accept `date_from`, `date_to`, `category`, `product` and `region` query parameters.

| Endpoint | Returns |
|---|---|
| `GET /api/filters` | Dropdown values and the data's date range |
| `GET /api/dashboard` | Key figures, plus whether filters are active |
| `GET /api/categories`, `/api/regions` | Revenue, units, orders and share of revenue |
| `GET /api/products` | Product table and top / lowest lists |
| `GET /api/trends?granularity=month\|quarter\|year` | Time series, trend, seasonality |
| `GET /api/sales` | Order table with `q`, `sort_by`, `order`, `page`, `page_size` |
| `GET /api/forecast?horizon=3\|6\|12` | Forecast, intervals, scope label |
| `GET /api/forecast/accuracy?horizon=…` | Held-out metrics and baseline comparison |
| `GET /api/insights?horizon=…` | Insights, recommendations, inventory signal |
| `GET /api/data-quality` | Cleaning summary |

## Design decisions

- **Correct analysis over fancy modeling.** One primary model, with baselines to prove it adds value.
- **No claim without evidence.** Seasonality, forecasts and recommendations only appear when the data supports them, and each says what it is based on.
- **Aggregation in SQL,** time-series and statistics in Pandas and statsmodels.
- **Accessible charts.** Every chart has a table view, series are identified by more than colour, and there are light and dark themes.
- Error metrics are plain NumPy, so scikit-learn is listed in `requirements.txt` but not currently used.

## Deployment: Render (API + database) and Vercel (website)

The API and its PostgreSQL database run on Render; the React site runs on Vercel and calls the API directly.

1. **Push to GitHub.** Commit and push this repository.
2. **Render:** *New > Blueprint*, pick the repository. `render.yaml` creates the `salescast-api` web service and the `salescast-db` database, and wires `DATABASE_URL`. When asked for `CORS_ORIGINS`, enter a placeholder for now. The first start loads `data/sales.csv` into the database.
3. **Check the API:** open `https://<your-api>.onrender.com/api/health`. It should return `{"status":"ok","sales_rows":19228}`.
4. **Vercel:** *Add New > Project*, import the repository, and set **Root Directory** to `frontend`. Add the environment variable `VITE_API_URL=https://<your-api>.onrender.com` (no trailing slash) and deploy.
5. **Allow the site to call the API:** in Render, set `CORS_ORIGINS=https://<your-site>.vercel.app` and let the service redeploy.

Notes: `VITE_API_URL` is read when the site is built, so redeploy on Vercel after changing it. On Render's free plan the API sleeps after 15 idle minutes (the first request then takes about a minute) and free databases expire after 30 days.
